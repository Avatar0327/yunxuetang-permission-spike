# Task4 public contracts and continuation

Task4 preserves the reviewed READ COMMITTED revision-only lock, then fresh person/company facts and version fencing. All high-risk mutations call that authority boundary before object/row locks. Native and Casbin select sources through genuinely separate existing engine paths; central normalization, scopes, SQL compiler and row predicates remain shared.

- `OrganizationFacts.person` now carries manager/job/display name for synchronous projection delivery. `OrganizationService.update` consumes its actual action plan and same-source person cap in addition to old/new company caps. Restoring disabled/deleted targets remains allowed to an authorized current administrator; historical status is never used for actor authentication. Normal department null clears reject. `syntheticMissingDepartment` is test-only abnormal-data injection.
- `ReportProjectionPort`, `TrainingProjectionPort`, `AccountProjectionPort` receive the same marked transaction client. Report owns current company/status/department/manager/job/name; training owns a minimal person projection for roster/team commands; account owns current person status. No module queries another module's private SQL tables. Independent services/RLS/outbox remain unproven.
- `EnrollmentService.change(identity,candidate,projectId,{operation,personIds})` accepts1..200 unique IDs. It validates every target before a single batch mutation. An authorized project role/appointment action and direct-team action are alternative sources. Team sources require team_enabled and managerId==actor and company/current-state constraints. Project capabilities remain independent of the team switch. Revocation races use the shared revision lock; no client ScopeSpec/grant/sourceId is accepted.
- `TrainingService.roster(...,search?,personId?)` uses one company-filtered relation for list/count/search. `personal(...,'progress'|'attachment')` first consumes that relation, returns protected synthetic data and never a storage URL. Whole-project save examines every roster company, including invisible rows. Project asynchronous export remains Task5.
- `CompanyGrantService.change` requires a selected active source membership with the exact delegable authz.company.grant action, its same-action target person cap, target internal status and both target/desired company bounds. It never borrows another role's capability. Grant/revoke trigger revision/dependency updates atomically.
- `AccountService.own` returns only actor/company/currency balances and debt. Management list/detail/source/export use separate exact actions with dataCompany caps and current target status. Offset validates both entries against its own action plan, locks sorted IDs after revision, and requires same person/company/currency plus debt/reward kinds. Audit records actual consumed amount. Own-wallet authorization never unlocks management sources.
- `departmentObjects` is organization-owned exact department enumeration. The registered department node permits only all; organization.department.move is distinct from person.update. The move command checks the complete subtree and destination parent IDs with the same central plan, current company cap and physical same-company/depth/cycle rules. Root parent null introduces no parent object. No new department SELF semantics were invented.

History/account use `NodeDefinition.capDimension`, propagated to ScopeSpec and validated in central binding. Their cap dimension is person-company-v1. ObjectSet exact subset checks retain that dimension, original selected membership, actor, revision and fields. `reportObjects`/`accountObjects` enumerate current people crossed with valid company caps even with zero existing facts/entries. Runtime sources decode only valid tagged two-string tuples into ScopeSpec.personCompanyPairs; the SQL compiler intersects pairs per source before pagination/count/aggregation/export. Pure candidate scope matching uses the same tuple predicate. Untagged legacy or unknown dimensions fail closed, and normal explicit original-source recheck is the migration route. Other object types retain exact object-ID caps. This fixes generated-row cutoff behavior under approved T-15; it does not create a new business authorization rule.
