# Task3 module ports and persistence contract

`src/contracts/ports.ts` defines trusted internal contracts. Bootstrap binds OrganizationFactsPort, TrainingFactsPort and KnowledgeFactsPort. Existing direct service construction uses equivalent default bindings for compatibility. These ports are not exposed as HTTP endpoints and never call Authority recursively.

| Public contract | Owning data and behavior |
|---|---|
| `OrganizationFacts.person(identity)` | Minimal current person/company/department/status facts from organization. |
| `OrganizationFacts.resolveScopeMembers(specs,revision)` | Existing version-bound bulk relation resolution; ALL/SELF avoid whole-person enumeration. |
| `TrainingFacts.appointments(identity)` | Training-owned appointments; no organization-private SQL. |
| `KnowledgeFacts.catalogs(identity)` | Category hierarchy/policy, course category/custom references, synthetic classroom membership. Central Authority normalizes subjects to ordinary course QueryPolicy sources. The resource SQL never switches on subject types. |
| `ReportProjection.person(db,fact)` | Report-owned synchronous projection update using the same marked transaction client. |
| `reportObjects / trainingObjects / knowledgeObjects(db,QueryPolicy)` | Owning-module exact business-object enumeration for delegation only. History uses report's current person projection. They consume central compiler predicates and do not interpret scope enums. |
| `authz/public.ts` | Central application-strategy entry points; exposes no repositories. |
| `knowledge.freeze_source_configs(tenant)` | Owning-module SQL transaction port, invoked by central dependency trigger; only knowledge private tables are changed within it. |

Protected mutations retain the reviewed protocol: `BEGIN ISOLATION LEVEL READ COMMITTED`; marked pinned client; revision-only `FOR UPDATE OF r`; then fresh revision/company/person reads and a revision fence. The new facts ports must use that same client. Reports do not join organization-private tables. Membership and role reads are authz-owned; role policy is canonical when present, while seeded legacy roles with null canonical policy retain local fixture compatibility. Editing a legacy role promotes its policy to canonical and fans out to all memberships without clearing overrides, active flags or provenance.

Derived membership data contains `delegation.sourceMembershipId,sourceActorId,revision,caps[]`; each cap binds node/action, exact permitted object IDs and raw fields. Normalization intersects saved caps with current scope. Recipient-relative SELF/department scopes are resolved independently before issuance. A source may not borrow another membership or appointment. Source and organization/object-set changes freeze derived configurations in the same transaction. Membership graph cycles have service and database checks. Recheck follows the original membership ID, not a newly created membership for the same role/person, and writes active/suspended audit details. Role mutations and rechecks also respect target member company caps. Recheck requires both the acting administrator and the original source actor to retain the recipient company; a broad rechecker cannot repair a missing original-source company cap. Capability/level validation does not resolve the proposed SELF/department scope against the grantor: exact subset comparison resolves the recipient context (and recipient jurisdiction) against the original source. Empty object sets still require explicit action/field delegability. An unassigned role template grants no membership; adding a recipient validates its actual set before issuance.

Category and custom policies persist selected source and a cap snapshot/version. The saved cap is the actual affected object set: a custom browse save/recheck uses its single course, while category saves/append/recheck follow the effective policy owner through inherited or forced descendants (including proposed force/inherit flags). Stored course browse overrides exclude that course from an unlocked category browse proposal. These affected IDs are trusted owning-module facts, never copied from a request DTO. Knowledge enumeration and live queries share the action-sensitive accessibility predicate: inaccessible courses remain maintainable, while browse/download remain blocked. Effective ancestry ignores frozen local grants. Forced/inherited policy overrides an earlier course custom policy; locked writes reject even for the creator. Public means authenticated current-tenant browse, never anonymous/cross-tenant exposure. Parent append uses a current revision preview and changes one named parent while retaining existing allows. Policy saves validate the whole retained set against the newly selected source before replacing provenance.

Freeze granularity is conservative: organization/company/object-set changes freeze all derived memberships and source-bound knowledge policies in the tenant; membership changes freeze dependency descendants and conservatively freeze source-bound knowledge policies. Knowledge course insertion/deletion and writes naming enabled/deleted/published/accessibility/uploader fields are object-set triggers. Saving custom browse alone does not trigger object-set freezing, so a validated save remains usable. Semantic object writes that name unchanged fields can still over-freeze. This is safe but may be expensive and inconvenient. Category/custom explicit recheck endpoints follow the stored original source membership and append active/suspended outcomes plus cap/version snapshots to knowledge.policy_audit. Authorized full policy saves also revalidate the selected source.

This is source-level modularity in a shared database. Cross-module foreign keys and a shared transaction coordinator are intentional. Independently deployed services would require a revision-consistent facts/projection/dependency protocol before the transaction client could be replaced; no independent database-role/RLS/service split is claimed. The synthetic KnowledgeFacts adapter materializes course/category policy references before source compilation; production-scale policy cardinality and Casbin source cost remain unmeasured. Exact object cap snapshots also enumerate potentially large business sets during delegation; large-cap storage/performance remains Task4 audit work. No full UI/production upload workflow or cloud storage adapter is implemented here.
