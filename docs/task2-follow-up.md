## Static table access map / splitability

- `report/service.ts` reads only `report.person_projection` and `report.learning_fact`; the SQL compiler emits bound `unnest` person relations and never joins organization tables.
- `report/exports.ts` reads/writes only `report.export_job` and calls ReportService. It never calls the object candidate per row.
- `organization/public.ts` owns private department/person scope reads; it uses central `resolveScope` semantics first against representative departments, then retrieves relevant people in one query. ALL and SELF skip enumeration.
- `authz/revision.ts` is the trusted central facts adapter and currently reads organization person plus authz revision/company_grant/session/membership and training appointment directly. Its queries should be moved behind explicit OrganizationFacts/TrainingFacts public ports before module splitting; this milestone does not claim a mechanically separable build.
- `organization/service.ts` owns person mutations but currently writes report projection and reads authz membership/revision via central services. Replace the projection SQL with a ReportProjection public application port, while retaining one database transaction or an independently proved revision-consistent projection protocol.
- `training/service.ts` owns project/roster/appointment SQL but currently reads person company directly for appointment target validation. Move that read to OrganizationPublic before enforcing static boundaries.
- Schema tenant-qualified FKs protect organization company/department/person, role memberships, appointments, rosters, report learning-to-current-person projection and export ownership. A full per-module DB-role privilege split and RLS are not implemented.
